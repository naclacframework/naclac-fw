Solana passes every account to your program as a raw `AccountInfo` pointer — a flat byte slice paired with a few flags for writability, signer status, and ownership. Nothing in the runtime enforces that you read the right account in the right slot or that its data matches the type you expect. Naclac's account wrappers close that gap: at context-initialization time, each wrapper validates ownership, writability, signer status, and type safety before your instruction logic ever runs. A mismatched account fails loudly at the boundary rather than silently corrupting state.

## Account Wrapper Types

<AccordionGroup>
  <Accordion title="Signer<'info>">
    `Signer<'info>` wraps an account that must have signed the transaction. Naclac checks `AccountInfo::is_signer` during context hydration and returns a `SignerNotPresent` error immediately if the condition is not met — your instruction body never executes.

    Use `Signer` for any account that must authorize the transaction: payers, authority keys, multisig members.

    ```rust
    #[derive(Accounts)]
    pub struct InitializeCtx<'info> {
        #[account(mut)]
        pub payer: Signer<'info>,
    }
    ```

    `Signer` does not deserialize account data. If you need the signer's account data (e.g., reading a user profile), pair it with `Account<'info, T>` instead and add the `signer` constraint.
  </Accordion>

  <Accordion title="Account<'info, T>  —  Standard mode">
    `Account<'info, T>` deserializes the raw account data bytes into a typed Rust struct `T` using Borsh. Before deserializing, it checks:

    - The account is owned by the expected program (derived from `T`'s `owner()` impl).
    - The first 8 bytes match `T`'s discriminator (a hash of the type name written by `#[component]`).

    Use `Account` in Standard mode when you need to read or mutate account fields as owned Rust values.

    ```rust
    pub counter_account: Account<'info, Counter>,
    ```

    When paired with the `mut` constraint, Naclac serializes the modified `T` back to the account's data buffer at the end of the instruction. This re-serialization is where Borsh's cost appears — `AccountLoader` (below) eliminates it.
  </Accordion>

  <Accordion title="AccountLoader<'info, T>  —  Optimized / Pinocchio mode">
    `AccountLoader<'info, T>` gives you a direct, in-place reference to account data without copying or deserializing it. Internally it uses `bytemuck::from_bytes_mut` to cast the raw data pointer to `&mut T`. Your struct `T` must implement `bytemuck::Pod` and `bytemuck::Zeroable` — Naclac's `#[component(zero_copy)]` macro derives both automatically.

    Use `AccountLoader` in Optimized or Pinocchio mode for all accounts that store structured data.

    ```rust
    pub counter_account: AccountLoader<'info, Counter>,
    ```

    Access the inner data via `.load()` (immutable) or `.load_mut()` (mutable):

    ```rust
    let counter = ctx.accounts.counter_account.load_mut()?;
    counter.count += 1;
    ```

    Because you are writing directly into the account's memory, there is no serialization step on the way out. The modified bytes are already in place.

    <Note>
      `AccountLoader` performs the same discriminator and ownership checks as `Account` — the difference is purely in how data is accessed after validation, not in how much validation occurs.
    </Note>
  </Accordion>

  <Accordion title="Program<'info, T>">
    `Program<'info, T>` validates that the passed account is an executable program with a specific program ID. It checks `AccountInfo::executable == true` and that the key matches the ID returned by `T::id()`.

    Use `Program` when your instruction performs CPI (Cross-Program Invocation) and you need to name the target program in the accounts list.

    ```rust
    pub system_program: Program<'info, System>,
    ```

    Common program types provided by Naclac's prelude: `System`, `Token`, `AssociatedToken`. You can also implement `Id` on a custom struct to reference your own programs.
  </Accordion>

  <Accordion title="Interface<'info, T>">
    `Interface<'info, T>` is like `Program` but accepts a set of valid program IDs rather than exactly one. Use it when your instruction is compatible with multiple program implementations — the canonical example is accepting either the original SPL Token program or Token-2022.

    ```rust
    pub token_program: Interface<'info, TokenInterface>,
    ```

    `TokenInterface` is exported from Naclac's prelude and accepts both `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` (SPL Token) and `TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb` (Token-2022). Token CPI helpers require the `spl-token` feature (Standard/Optimized mode) or the `pinocchio-token` feature (Pinocchio mode). Use `Interface` any time you want your program to be forward-compatible with new program upgrades without a redeployment.
  </Accordion>
</AccordionGroup>

## Zero-Copy Field Helper Types

When you use `#[component(zero_copy)]` (Optimized or Pinocchio mode), every field in your component struct must implement `bytemuck::Pod`. Rust's native `bool` and `Option<T>` are not `Pod`-compatible because their in-memory representations have undefined bit patterns. Naclac's prelude exports two drop-in replacements:

### `Bool`

A `#[repr(transparent)]` wrapper around `u8` that implements `Pod`, `Zeroable`, and common comparison traits. Use it anywhere you would use `bool` inside a zero-copy component.

```rust
use naclac_lang::prelude::*;

#[component(zero_copy)]
pub struct Config {
    pub is_paused: Bool,   // use Bool, not bool
    pub owner: Pubkey,
}
```

Convert to/from Rust `bool` with `From`/`Into`:

```rust
// Setting
config.is_paused = Bool::from(true);

// Reading
if bool::from(config.is_paused) {
    return Err(CounterError::Paused.into());
}
```

### `Opt<T>`

A `#[repr(C)]` optional value that implements `Pod` and `Zeroable` for any `Pod` inner type `T`. It stores the value inline alongside a `has_value: u8` discriminant and 7 bytes of padding to keep the layout aligned. Use it anywhere you would use `Option<T>` inside a zero-copy component.

```rust
#[component(zero_copy)]
pub struct UserRecord {
    pub authority: Pubkey,
    pub referrer: Opt<Pubkey>,  // use Opt<Pubkey>, not Option<Pubkey>
    pub stake_amount: u64,
}
```

Create and read `Opt<T>` values:

```rust
// Creating
record.referrer = Opt::new(referrer_pubkey);      // Some equivalent
record.referrer = Opt::none(Pubkey::default());   // None equivalent

// Reading
if record.referrer.has_value != 0 {
    let referrer = record.referrer.value;
    // ...
}
```

You can also convert from `Option<T>` via `From`:

```rust
record.referrer = Opt::from(Some(referrer_pubkey));
record.referrer = Opt::from(None::<Pubkey>);
```

<Note>
  `Bool` and `Opt<T>` are only needed inside `#[component(zero_copy)]` structs. In Standard mode, use Rust's native `bool` and `Option<T>` as normal — Borsh handles their serialization automatically.
</Note>

## The Context\<T\> Type

Every instruction handler receives a single `ctx: Context<T>` argument, where `T` is the accounts struct you defined. `Context<T>` is the primary way you access everything your instruction needs from the runtime.

```rust
#[instruction]
pub fn increment(ctx: Context<IncrementCtx>) -> Result<()> {
    let counter = ctx.accounts.counter_account.load_mut()?;
    counter.count += 1;
    Ok(())
}
```

The three fields you will use most often:

| Field | Type | Description |
|---|---|---|
| `ctx.accounts` | `&mut T` | Your typed accounts struct. Access individual accounts as fields: `ctx.accounts.payer`, `ctx.accounts.counter_account`, etc. |
| `ctx.bumps` | `BumpSeeds` | The canonical bump bytes for every PDA in `T` that was derived with the `bump` constraint. Access them by field name: `ctx.bumps.counter_account`. Store bumps in your account data at initialization so you can reconstruct the signer seeds in later CPIs. |
| `ctx.program_id` | `&Pubkey` | The executing program's public key. Useful when you need to pass your own program ID to a CPI or record it in account data. |

## Account Constraints

The `#[account(...)]` attribute on fields inside your accounts struct lets you express validation rules declaratively. Naclac emits the corresponding checks into the context-hydration code — you never write `require!(...)` boilerplate for standard validations.

### Constraint reference

| Constraint | Description |
|---|---|
| `mut` | Marks the account as writable. Naclac fails context init if the runtime did not pass the account with write permission. |
| `init` | Initializes the account by invoking the System Program's `create_account` CPI. Requires `payer = <signer_field>` and `space = <usize_expr>`. |
| `init_if_needed` | Like `init` but only creates the account if it does not already exist. Useful for idempotent setup instructions. |
| `seeds = [expr, ...], bump` | Derives the expected PDA from the provided seeds and your program ID, then asserts the passed address matches. The canonical bump is stored in `ctx.bumps.<field_name>`. |
| `has_one = field` | Asserts that `account.field == ctx.accounts.field.key()`. Use this to tie an account to a specific authority or related account without writing a manual `require!`. |
| `owner = program_id` | Asserts `AccountInfo::owner == program_id`. Useful when the default ownership check (derived from `T`) is insufficient. |
| `address = pubkey` | Asserts the account's public key equals `pubkey` exactly. Use for singleton accounts like the System Program or a known oracle. |
| `close = destination` | Closes the account at the end of the instruction: zeroes the data, transfers all lamports to `destination`, and sets the owner to the System Program. |

### PDA initialization example

```rust
#[derive(AccountsLoader)]
pub struct InitializeCtx<'info> {
    #[account(mut)]
    pub payer: Signer<'info>,

    #[account(
        init,
        payer = payer,
        space = Counter::SPACE,
        seeds = [SEED_COUNTER],
        bump
    )]
    pub counter_account: AccountLoader<'info, Counter>,

    pub system_program: Program<'info, System>,
}
```

Naclac compiles this into a context hydration sequence that:
1. Derives the PDA from `[SEED_COUNTER]` and your program ID.
2. Confirms the passed `counter_account` key matches the derived PDA.
3. Invokes `system_program::create_account` funded by `payer`, allocating exactly `Counter::SPACE` bytes.
4. Writes the discriminator into the first 8 bytes.
5. Stores the canonical bump so it is available via `ctx.bumps.counter_account`.

## PDA Derivation

When you use the `seeds = [...], bump` constraint, Naclac finds the canonical bump by searching from 255 downward until `create_program_address` succeeds. That bump is then available in `ctx.bumps.<field_name>` as a `u8`.

Store the bump in your component at initialization time so you can reconstruct signer seeds in future CPIs without re-searching:

```rust
#[instruction]
pub fn initialize(ctx: Context<InitializeCtx>) -> Result<()> {
    let mut counter = ctx.accounts.counter_account.load_init()?;
    counter.bump = ctx.bumps.counter_account;
    counter.count = 0;
    Ok(())
}
```

Later, when you need the PDA as a signer for a CPI:

```rust
let seeds = &[SEED_COUNTER, &[counter.bump]];
let signer_seeds = &[&seeds[..]];
```

Define all seed constants in `src/constants.rs` so the same byte values appear in both your Rust program and Naclac's generated TypeScript client:

```rust
// constants.rs
pub const SEED_COUNTER: &[u8] = b"counter_v2";
```

<Note>
  **The `SPACE` constant:** When you annotate a struct with `#[component]` (or `#[component(zero_copy)]`), Naclac automatically calculates a `SPACE` associated constant on the type. This constant accounts for the 8-byte discriminator prefix plus the size of all fields. Use `Counter::SPACE` in your `init` constraint rather than computing the byte count manually — if you add fields to the component, `SPACE` updates automatically on the next build.
</Note>
