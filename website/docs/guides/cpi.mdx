Cross-Program Invocations (CPIs) let your Naclac program call instructions on other deployed Solana programs. Naclac provides type-safe CPI helpers for both built-in Solana programs (system program, SPL Token) and external Naclac programs — and they work correctly across all three execution modes (Standard, Zero-Copy, and Pinocchio).

## Built-In CPIs (System Program, SPL Token)

Naclac re-exports `system_program` helpers from `naclac_lang::prelude`. To transfer SOL between accounts, call `system_program::transfer` with a `CpiContext`:

```rust
use naclac_lang::prelude::*;

naclac_lang::prelude::system_program::transfer(
    CpiContext::new(
        ctx.accounts.system_program.to_account_info(),
        naclac_lang::prelude::system_program::Transfer {
            from: ctx.accounts.payer.to_account_info(),
            to: ctx.accounts.recipient.to_account_info(),
        },
    ),
    amount_lamports,
)?;
```

`CpiContext::new` takes two arguments: the program's `AccountInfo` (the callee), and the accounts struct for that CPI call. The trailing `?` propagates any `ProgramError` returned by the callee back to your caller.

For SPL Token operations, add the `spl-token` feature to your `Cargo.toml` and use the helpers in `naclac_lang::prelude::token`. The API mirrors the system program pattern — `token::transfer`, `token::mint_to`, `token::burn`, etc.

## Calling a Naclac Program via `#[naclac_interface]`

To call an external Naclac program from your own, use the `#[naclac_interface]` macro from the `naclac-interface` crate. This generates a type-safe `cpi` module with the correct discriminators and account metas for the target program.

Add the dependency to your caller's `Cargo.toml`:

```toml
[dependencies]
naclac-interface = "0.1.0"
```

Define the interface in your caller crate — one function per instruction you want to invoke:

```rust
use naclac_interface::naclac_interface;
use naclac_lang::prelude::*;

#[naclac_interface]
mod my_counter_interface {
    use super::*;

    pub fn increment(ctx: Context<Increment>) -> Result {
        Ok(())
    }
}

#[derive(Accounts)]
pub struct Increment<'info> {
    pub authority: Signer<'info>,
    pub counter_account: Account<'info, Counter>,
}
```

The `#[naclac_interface]` macro reads the function signatures and accounts structs, then generates a `cpi` submodule with ready-to-call helpers and a nested `accounts` module with the matching accounts struct:

```rust
// Invoke via the generated helper
my_counter_interface::cpi::increment(
    CpiContext::new(
        program_account.to_account_info(),
        my_counter_interface::cpi::accounts::Increment {
            authority: authority.to_account_info(),
            counter_account: counter_account.to_account_info(),
        },
    ),
)?;
```

The generated helper constructs the correct 8-byte discriminator (`SHA256("global:increment")`), serializes any instruction arguments, and calls `invoke` (or `invoke_signed` for PDAs) on your behalf. Because the discriminator is derived from the function name at compile time, you get a compile-time guarantee that the CPI call matches the target program's IDL.

## PDA Signer CPIs

When your program's PDA needs to sign a CPI (e.g., a vault PDA authorizing a transfer), use `CpiContext::new_with_signer` and pass the PDA's seeds:

```rust
let seeds = &[SEED_COUNTER, &[bump]];
let signer_seeds = &[&seeds[..]];

system_program::transfer(
    CpiContext::new_with_signer(
        ctx.accounts.system_program.to_account_info(),
        system_program::Transfer {
            from: vault.to_account_info(),
            to: recipient.to_account_info(),
        },
        signer_seeds,
    ),
    amount,
)?;
```

`signer_seeds` is a slice-of-slices-of-slices — one inner slice per PDA signer, where each inner slice contains that PDA's seeds. The Solana runtime uses these seeds to verify the PDA's signature authority before executing the CPI.

Naclac pre-allocates stack space for CPI signer arrays using the constants `MAX_CPI_SIGNERS` (default: 4) and `MAX_CPI_SEEDS_PER_SIGNER` (default: 16) from `naclac_lang::prelude`. These conservative defaults keep your stack frame well within Solana's 4 KB stack limit. If your program requires more signers, override these constants before importing the prelude.

## Pinocchio Mode CPIs

In Pinocchio mode (`#![no_std]`), CPI signer seeds are stack-allocated using `MaybeUninit` arrays sized by `MAX_CPI_SIGNERS` and `MAX_CPI_SEEDS_PER_SIGNER`. This avoids any heap allocation during the CPI path.

You do not need to change your interface definition or call sites when targeting Pinocchio. The generated `#[naclac_interface]` helpers detect the active backend at compile time via Cargo features and emit the correct invocation path:

- **Standard** (`feature = "solana"`): calls `solana_program::program::invoke` / `invoke_signed`
- **Pinocchio** (`feature = "pinocchio"`): calls `pinocchio::cpi` with stack-allocated instruction accounts

The interface definition you write is identical in both cases — the backend routing is transparent.

<Note>
`naclac-interface` is backend-agnostic by design. The same interface definition and call site compiles correctly for Standard, Zero-Copy, and Pinocchio modes. The generated helpers auto-detect which backend is active based on the `pinocchio` Cargo feature and emit the appropriate `invoke` / `invoke_signed` call. You never need to write separate CPI code for different execution modes.
</Note>
