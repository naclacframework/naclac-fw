Events let your program emit structured, indexed data during instruction execution. Off-chain clients can subscribe to these events in real time using the generated TypeScript SDK, making it straightforward to build reactive UIs, indexers, and analytics pipelines on top of your program.

## Defining an Event

Create an event struct and annotate it with `#[event]`. Place your events in `src/events.rs`:

```rust
use naclac_lang::prelude::*;

#[event]
pub struct CounterIncremented {
    pub new_count: u64,
    pub timestamp: i64,
}
```

For zero-copy or Pinocchio mode, use `#[event(zero_copy)]`:

```rust
#[event(zero_copy)]
pub struct CounterIncremented {
    pub new_count: u64,
    pub timestamp: i64,
}
```

Both variants inject an 8-byte discriminant at compile time — computed from `SHA256("event:<TypeName>")` — so the TypeScript SDK can unambiguously identify the event type when parsing transaction logs.

In standard mode, `#[event]` derives `BorshSerialize` and emits the payload via `sol_log_data`. In zero-copy mode, the macro generates allocation-free emission logic using `bytemuck::bytes_of` to cast the struct to raw bytes and passes them directly to `sol_log_data` — no intermediate heap buffer is created. The discriminant is prepended to the serialized payload in both cases.

## Emitting Events

Call the `emit!` macro anywhere inside your instruction body. Import the event type first:

```rust
use crate::events::CounterIncremented;

emit!(CounterIncremented {
    new_count,
    timestamp: unix_timestamp()?,
});
```

`emit!` supports both explicit `field: value` syntax and shorthand `field` syntax (where a local variable with the same name is used as the value). You can mix both in the same call:

```rust
let new_count = process_increment(counter_account)?;

emit!(CounterIncremented {
    new_count,                    // shorthand: uses local `new_count`
    timestamp: unix_timestamp()?, // explicit value
});
```

The macro expands to:
1. Create a default instance of the event struct.
2. Set each field via `Into` conversion (so `u64` fields accept `u64`, `i64` fields accept `i64`, etc.).
3. Call `.emit()` on the struct, which writes the discriminant + serialized payload to the transaction log via `sol_log_data`.

## Listening for Events in TypeScript

The TypeScript SDK generated by `naclac generate` creates a `waitFor<EventName>` helper for every event type defined in your program. Start listening **before** you send the transaction — the event is emitted inside the transaction and may resolve before your `await rpc()` call returns:

```typescript
// Start listening before sending the transaction
const eventPromise = client.waitForCounterIncremented({ timeoutMs: 10000 });

await client
  .increment({})
  .accounts({ authority: payer.address, counterAccount: counterPda })
  .rpc();

const event = await eventPromise;
if (event) {
  console.log("New count:", event.newCount);
}
```

`waitForCounterIncremented` returns a `Promise<CounterIncrementedEvent | null>`. It resolves with the event payload if the event is captured within `timeoutMs` milliseconds, or `null` if the timeout expires. Field names are camelCased in the TypeScript interface (`new_count` → `newCount`).

Run `naclac generate` after any changes to your event structs to keep the TypeScript types in sync with your on-chain program.

## Event vs Transaction Logs

Naclac events are emitted as raw byte data appended to the transaction's log output via the `sol_log_data` syscall. They are **not** stored in account state — they exist only in the transaction record.

The TypeScript SDK retrieves events by fetching the confirmed transaction by its signature and parsing the `logMessages` array. The SDK identifies event payloads by their 8-byte discriminant prefix, deserializes the remaining bytes, and returns the typed event object.

Because events live in transaction logs, they are:
- **Permanent** — available as long as the transaction record is accessible on an RPC node or archive.
- **Lightweight** — they don't consume account storage rent.
- **Not queryable on-chain** — your program cannot read back an event it previously emitted; use account state for that.

<Tip>
Always start the `waitFor<EventName>` listener **before** submitting the transaction. If you await the transaction first and then call `waitFor<EventName>`, the event may have already been emitted and its log data will no longer be available from the RPC. The pattern `const eventPromise = client.waitForX(...); await tx.rpc(); const event = await eventPromise;` guarantees you never miss it.
</Tip>
