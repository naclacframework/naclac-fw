Naclac Execution Modes: Standard, Optimized, Pinocchio

Compare Naclac's three execution modes — Standard, Optimized, and Pinocchio — and choose the right balance of ergonomics and compute efficiency.

Naclac lets you pick exactly how your program compiles and executes on the Solana Virtual Machine (SVM). Each mode generates different underlying code from the same macros — you write #[naclac_program], #[component], and #[instruction] the same way regardless of which mode you choose. What changes is the runtime dependency, memory strategy, and serialization layer that Naclac emits under the hood. Pick the mode that fits your current priorities: fastest time-to-ship, balanced compute savings, or absolute minimum compute unit usage.

  • Standard
  • Optimized
  • Pinocchio

Standard (solana-program + Borsh)

Standard mode is the default. It targets the solana_program crate with std enabled and uses Borsh for all serialization boundaries — the same approach used by most Solana programs today.

How it works

  • Uses the solana_program crate with the standard library (std) fully available.
  • Account data and instruction arguments are heap-allocated using familiar types like Vec<T> and String.
  • Instruction arguments implement BorshSerialize / BorshDeserialize — Naclac's macro codegen derives these automatically from your field definitions.
  • Account context structs use #[derive(Accounts)], which validates ownership, writability, and signer status at context-initialization time.

When to use Standard mode

  • You want maximum compatibility with existing tooling, explorers, and SDKs.
  • You're prototyping or iterating quickly and want the fastest path from idea to deployed program.
  • Your program is not compute-unit constrained and the ergonomics of heap allocation are more valuable than micro-optimization.

Cargo feature: default (the borsh and solana features are enabled out of the box)

Copy
[dependencies]
naclac-lang = "0.1.0"
# default features enable borsh + solana-program

No additional feature flags are required. When you run naclac init without extra flags, your project starts in Standard mode.

Optimized (solana-program + Zero-Copy)

Optimized mode retains the solana_program crate and std, but replaces Borsh deserialization with zero-copy memory mapping via bytemuck. Account data is accessed in-place — no copy, no allocation, no deserialization loop.

How it works

  • Still uses solana_program so all existing helpers (system program CPI, SPL token, etc.) remain available.
  • Account data structs are memory-mapped using bytemuck::Pod and bytemuck::Zeroable. The runtime simply casts the raw account data pointer to a typed reference.
  • Instruction arguments use ZcVec<'info, T> and ZcString<'info> instead of Vec<T> and String — these are view types that reference the transaction data buffer directly, eliminating allocator calls at the argument layer.
  • Account context structs switch from #[derive(Accounts)] to #[derive(AccountsLoader)], which uses the zero-copy loading path.

When to use Optimized mode

  • Your program processes moderately large account data and Borsh deserialization cost is measurable in your compute budget.
  • You want lower compute unit usage without giving up std and the full solana_program ecosystem.
  • You are migrating an existing program incrementally toward better performance.

Cargo feature: zero-copy — activated automatically when you annotate your program with #[naclac_program(zero_copy)] and your components with #[component(zero_copy)].

Copy
[features]
default = []
# zero-copy mode is activated via #[naclac_program(zero_copy)] and #[component(zero_copy)]

In lib.rs:

Copy
#[naclac_program(zero_copy)]
pub mod my_counter {
    // ...
}

And on each data component:

Copy
#[component(zero_copy)]
pub struct Counter {
    pub count: u64,
    pub bump: u8,
}

Pinocchio (no_std + Zero-Copy)

Pinocchio mode replaces the solana_program crate entirely with the pinocchio crate and compiles your program as #![no_std]. The generated code minimizes heap allocations to the absolute minimum required for Solana program execution.

How it works

  • Uses pinocchio instead of solana_program. Your crate declares #![no_std] and links the alloc crate for any unavoidable allocations.
  • All account data access is zero-copy, identical to Optimized mode.
  • CPI signer seeds are stack-allocated using MaybeUninit arrays — no Vec wrapping them at call sites.
  • Naclac wraps pinocchio's AccountView in its own AccountInfo<'info> newtype, so your instruction code uses the same AccountInfo API regardless of backend.

When to use Pinocchio mode

  • You are writing a high-frequency program (e.g., a DEX matching engine, a lending liquidator) where every compute unit matters.
  • You want the absolute minimum CU cost possible from a Naclac-generated program.
  • Your team is comfortable working without std and you have already audited your dependencies for no_std compatibility.

Cargo feature: pinocchio

Copy
[features]
default = ["pinocchio"]
pinocchio = ["naclac-lang/pinocchio"]

In lib.rs:

Copy
#![no_std]
use naclac_lang::prelude::*;

#[naclac_program]
pub mod my_counter {
    // ...
}

SPL Token in Pinocchio mode: The standard spl_token crate is not available in no_std environments. To interact with SPL Token accounts from Pinocchio mode, add the pinocchio-token feature to your dependency on naclac-lang:

Copy
naclac-lang = { version = "0.1.0", features = ["pinocchio", "pinocchio-token"] }

This pulls in the pinocchio-token crate, which provides no_std-compatible mint, token account, and transfer CPI helpers. Token-2022 is available via pinocchio-token-2022.

Switching Modes

Mode is set at project initialization via naclac init --mode <standard|optimized|pinocchio> and controls which Cargo features are active in your program crate. To change modes on an existing project:

  1. Update Cargo.toml in your program crate — add or remove the pinocchio / zero-copy features as needed.
  2. Update your macro attributes — change #[naclac_program] to #[naclac_program(zero_copy)] (Optimized) or leave it plain for Standard and Pinocchio; Pinocchio mode is driven by the Cargo feature rather than a macro argument.
  3. Update #[component] annotations — add (zero_copy) to each data struct when moving to Optimized or Pinocchio.
  4. Add #![no_std] to lib.rs when moving to Pinocchio.
  5. Run naclac build to confirm the new mode compiles cleanly before updating tests.

You do not need to rewrite instruction logic or constraint annotations when switching modes — the #[instruction], #[account(...)], and #[system] attributes are mode-agnostic.
