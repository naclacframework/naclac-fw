Testing & Deployment

Deploy a Naclac Program to Localnet, Devnet, or Mainnet

Deploy your compiled Naclac program to localnet, devnet, or mainnet by configuring the cluster in Naclac.toml and running naclac deploy.

After building your program with naclac build, deploy it to any Solana cluster in a single command. Naclac reads the cluster and wallet from Naclac.toml and calls the Solana program deploy tool automatically — no manual solana program deploy flags required.

Configure Your Target Cluster

Open Naclac.toml and set the cluster and wallet values under [provider]:

Copy
[provider]
cluster = "devnet"   # localnet | devnet | testnet | mainnet | custom RPC URL
wallet = "~/.config/solana/id.json"

Naclac maps the cluster name to the canonical RPC URL at deploy time:

cluster valueRPC endpoint used
localnethttp://127.0.0.1:8899
devnethttps://api.devnet.solana.com
testnethttps://api.testnet.solana.com
mainnethttps://api.mainnet-beta.solana.com
Any URLUsed as-is

If you use a private RPC endpoint (e.g. from QuickNode or Helius), paste the full URL directly:

Copy
cluster = "https://your-rpc.quicknode.pro/abc123"

Naclac detects that the value starts with http and passes it through to the Solana CLI without modification.

Deploying

Deploy all programs

Copy
naclac deploy

Naclac scans target/deploy/ for .so files, then calls solana program deploy once for each file found, passing the cluster URL and wallet keypair it read from Naclac.toml. Each program's deployment output — including the program ID and transaction signature — is printed to stdout as it completes.

Deploy a specific program

Copy
naclac deploy my_counter

Pass the program name (matching the filename stem in target/deploy/, without the .so extension) to deploy only that program. This is useful in workspaces with multiple programs when you want to redeploy just one.

If target/deploy/ is missing or contains no .so files, Naclac exits with an error reminding you to run naclac build first.

Fund Your Wallet

Before deploying to devnet or testnet, make sure your wallet has enough SOL to cover the rent-exempt storage for the program account. Use the built-in airdrop command:

Copy
naclac airdrop 2

This airdrops 2 SOL to the wallet configured in Naclac.toml. Omit the amount to use the default of 1 SOL:

Copy
naclac airdrop

The airdrop command targets the same cluster as the rest of your workflow — no extra flags needed. Note that devnet and testnet faucets enforce per-request limits; 2 SOL is the maximum per airdrop on devnet.

Program Keypairs

Each program in your workspace has a dedicated deploy keypair stored at:

Copy
target/deploy/<program_name>-keypair.json

The public key of this keypair is the program ID — the on-chain address where your program lives after deployment. Naclac generates these keypairs automatically the first time you run naclac build and writes the resulting program ID into both lib.rs and Naclac.toml so everything stays in sync.

Keep these keypair files safe. They are required to upgrade the program later. Add target/deploy/ to your .gitignore (Naclac does this by default) to avoid accidentally committing secret key material to version control. Back them up to a secure location separately.

Resume Failed Deployments

Deploying a large program or a program to a congested network can occasionally fail mid-upload. When this happens, the Solana CLI has already written part of the program data to a temporary buffer account on-chain.

To resume, simply re-run the same command:

Copy
naclac deploy

The underlying solana program deploy call detects the existing buffer account associated with your keypair and continues the upload from where it left off, rather than starting over. This saves both time and SOL (you don't pay for already-uploaded data again).

If you need to reclaim the SOL locked in a stale buffer from a previous failed run, use:

Copy
solana program close --buffers

Registering the IDL On-Chain

The Interface Definition Language (IDL) file describes your program's instructions, accounts, and types in a machine-readable JSON format. Uploading it on-chain allows clients, explorers, and indexers to decode your program's transactions automatically.

After a successful deploy, initialize the on-chain IDL account by passing the program's public key:

Copy
naclac idl init <PROGRAM_ID>

Replace <PROGRAM_ID> with the base58 program address printed by naclac deploy. This uploads the IDL JSON to a program-derived account associated with your program's ID. Once registered, tools like Solana Explorer can display human-readable instruction names and argument values for any transaction that calls your program.

To update an already-registered IDL after rebuilding and redeploying, run naclac idl init again with the same program ID — Naclac detects the existing IDL account, resizes it if necessary, and overwrites the stored data.

Mainnet deployments are permanent. Once a program is deployed to mainnet, the program account and its data exist on-chain indefinitely. Upgrades are possible only if the upgrade authority keypair is still available — if you lose it, the deployed binary can never be changed. Test thoroughly on devnet before targeting mainnet, and keep your upgrade authority keypair backed up securely.
