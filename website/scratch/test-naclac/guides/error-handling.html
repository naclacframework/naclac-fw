Building Programs

Handle Program Errors with #[error_code] in Naclac

Define typed program errors with #[error_code] and use the require! macro to return descriptive errors from your Naclac instructions.

Naclac programs return strongly-typed errors using the #[error_code] macro. Each variant maps to a unique numeric error code that off-chain clients can match against, and doc comments on each variant become human-readable messages in the IDL — so your users see "User is not authorized to perform this action." instead of a raw number.

Defining Error Codes

Create your error enum in src/errors.rs and annotate it with #[error_code]:

Copy
use naclac_lang::prelude::*;

#[error_code]
pub enum CounterError {
    /// User is not authorized to perform this action.
    Unauthorized,
    /// The counter has reached the maximum value.
    Overflow,
}

Error codes start at 6000 by default — the same base offset used by Anchor, so Naclac error codes are compatible with Anchor client libraries and explorers that decode program errors. The variants are assigned codes in declaration order:

VariantCode
Unauthorized6000
Overflow6001

Doc comments (/// ...) on each variant are extracted at compile time and embedded in the IDL as the error message. The TypeScript client uses these messages to surface human-readable errors.

You can define multiple error enums in the same program. Each enum is independent — every enum starts its variant numbering from 6000 with its own zero-indexed variants. To avoid collisions across enums, use a single consolidated error enum or reserve distinct variant ranges manually.

Using require! in Instructions

The require! macro is the idiomatic way to assert a condition and return an error if it fails. Import your error enum and call require! with the condition and the error variant:

Copy
use naclac_lang::prelude::*;
use crate::errors::CounterError;

#[instruction]
pub fn increment(ctx: Context<Increment>) -> Result {
    require!(
        ctx.accounts.authority.key() == ctx.accounts.counter_account.authority,
        CounterError::Unauthorized
    );

    ctx.accounts.counter_account.count += 1;

    Ok(())
}

require!(condition, error) expands to:

Copy
if !(condition) {
    return Err((error).into());
}

The .into() conversion is handled by the #[error_code] macro, which implements From<CounterError> for ProgramError automatically. This means you can use ? with Result<T, CounterError> functions anywhere in your instruction body.

Returning Errors Manually

For more complex control flow, return errors directly without require!:

Copy
if counter.count == u64::MAX {
    return Err(CounterError::Overflow.into());
}

Or propagate errors from helper functions using ?:

Copy
let new_count = process_increment(counter)?;  // returns Result<u64, CounterError>

Because #[error_code] implements Into<ProgramError> for your enum, both patterns work seamlessly with Naclac's Result type alias.

Error Codes in the IDL

Every variant in an #[error_code] enum is included in the IDL's errors array. The IDL entry for each variant contains:

  • code — the numeric error code (starting at 6000)
  • name — the variant name as a string
  • msg — the doc comment text, or the variant name if no doc comment is present

Example IDL output for CounterError::Unauthorized:

Copy
{
  "code": 6000,
  "name": "Unauthorized",
  "msg": "User is not authorized to perform this action."
}

The generated TypeScript SDK client maps these codes to typed error objects. When a transaction fails with error code 6000, the client throws an error with the msg field populated — no raw number decoding needed.

Built-In Naclac Errors

Naclac itself uses NaclacError — a framework-level error type defined in naclac_lang::prelude — for infrastructure-level failures that occur before your instruction code runs:

VariantWhen it fires
InvalidInstructionDataInstruction data is too short to contain a valid discriminator or arguments
InvalidDiscriminatorThe 8-byte discriminator does not match any registered instruction
InvalidAccountOwnerAn account's owner program does not match the expected program
InvalidAccountDataAn account's data cannot be interpreted as the expected component type

You do not need to handle NaclacError directly — these are returned from load_and_validate and propagated automatically. If you see one of these errors in a client, it indicates a client-side bug (wrong accounts passed, wrong program ID, stale IDL) rather than a business-logic error.

There are two distinct categories of errors in a Naclac program. Constraint errors are generated automatically by #[derive(Accounts)] / #[derive(AccountsLoader)] when an #[account(...)] constraint fails (e.g., wrong signer, mismatched PDA, failed has_one). These fire before your instruction body runs. Business-logic errors are the ones you define with #[error_code] and return explicitly with require! or Err(...) — these fire inside your instruction body when domain rules are violated. Treat them as two separate layers: constraints guard account integrity, #[error_code] guards program invariants.
