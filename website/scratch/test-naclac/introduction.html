Naclac: Hyper-Optimized Native Solana Smart Contracts

Naclac is a Rust framework for writing native Solana smart contracts. Pick an execution mode and use procedural macros to eliminate boilerplate.

Naclac is a Rust framework that lets you write native Solana smart contracts without sacrificing developer ergonomics for performance. You pick an execution mode that matches your performance budget—from Borsh-serialized programs compatible with the full Solana tooling ecosystem all the way to zero-allocation, no_std programs built on the Pinocchio runtime—and Naclac's procedural macro system handles the instruction dispatching, account validation, IDL generation, and TypeScript client generation for you.

Naclac targets Rust developers who want the compute-unit efficiency of hand-rolled native programs and the productivity of a structured framework. If you have outgrown Anchor's overhead but don't want to manage every byte of account parsing by hand, Naclac sits exactly in that space.

What Makes Naclac Different

Three Execution Modes

Naclac gives you a single programming model across three execution modes. You choose the mode at workspace creation time; your program structure and macro API remain identical regardless of the mode you pick.

Automatic IDL and TypeScript SDK Generation

Running naclac build compiles your SBF binary and then automatically:

  1. Parses your macro-annotated source to produce an IDL at target/idl/<program_name>.json
  2. Writes TypeScript type definitions to target/types/<program_name>.ts
  3. Runs naclac generate to produce a fully-typed TypeScript SDK client under clients/src/generated/

Your on-chain interface and your off-chain client always stay in sync—you never maintain them separately.

The Macro System

Naclac's procedural macros cover every layer of a Solana program:

MacroPurpose
#[naclac_program]Generates the BPF entrypoint and an 8-byte discriminator-based instruction dispatcher
#[naclac_program(zero_copy)]Same as above, optimized for zero-copy account loading
#[component]Derives account struct layout with BorshSerialize / BorshDeserialize and computes SPACE
#[component(zero_copy)]Derives account struct layout using bytemuck::Pod for zero-copy deserialization
#[event]Declares a program event that is emitted via emit!() and captured by the generated client
#[event(zero_copy)]Zero-copy variant of #[event]
#[error_code]Derives typed program errors with human-readable messages
#[derive(Accounts)]Validates and deserializes a set of Borsh accounts for an instruction context
#[derive(AccountsLoader)]Validates and zero-copy-loads a set of accounts for an instruction context
#[naclac_interface]Generates strongly-typed CPI builder structs from a shared interface definition so callers never construct instruction data by hand

Discriminators follow the Anchor convention—8 bytes computed as the first 8 bytes of SHA256("global:<fn_name>"))—so generated clients are compatible with Anchor-aware tooling.

CPI Support via naclac-interface

To call your Naclac program from another program, depend on the companion naclac-interface crate and annotate your shared interface with #[naclac_interface]. The macro generates strongly-typed CPI builder structs so callers never construct instruction data by hand.

Version Management with nacvm

nacvm is the optional Naclac version manager. Use it to install, switch between, and remove specific CLI versions without touching your system PATH manually.

Copy
nacvm install v0.2.0   # install a specific version
nacvm use v0.2.0       # activate it for the current shell
nacvm list             # show all installed versions
nacvm uninstall v0.1.0 # remove an old version

When To Use Each Mode

Standard — Start here. Use Standard when you want the widest compatibility with existing Solana clients and tooling, when your program's compute budget isn't under pressure, or when your team is already familiar with Borsh-serialized account data. All Anchor-compatible wallets and explorers can decode your accounts without any extra configuration.

Optimized — Switch to Optimized when profiling shows that account deserialization is consuming a meaningful fraction of your compute budget. The zero_copy attribute replaces Borsh with bytemuck-based casting, which eliminates heap copies on every account load. Your program still targets solana-program so the rest of the ecosystem integration remains identical.

Pinocchio — Reserve Pinocchio for programs where every compute unit counts and you have full control over all on-chain callers. The pinocchio crate provides a no_std, zero-allocation runtime that avoids the global allocator entirely. You lose some ergonomic conveniences and certain standard library utilities, but you gain the absolute lowest possible execution cost. This mode is ideal for high-frequency AMM programs, compression-tree processors, and any program called inside tight CPI chains.
