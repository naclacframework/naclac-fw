compile-fail suite: status and plan

Goal: every error message the macros can emit has a failing fixture and a
valid counterpart, run under every runtime and layout it applies to. Nothing
runs locally; CI (.github/workflows/compile-fail.yml) is the only runner.

Design (written 2026-11-21)
- Runner: tests/compile_fail.rs runs one configuration per `cargo test`:
  --no-default-features --features RUNTIME,LAYOUT, for the five combinations
  solana,bytemuck  solana,borsh  solana,wincode  pinocchio,bytemuck  pinocchio,wincode.
  src/lib.rs exists only so trybuild forwards the features to naclac-lang.
- Fixture folders: tests/fail and tests/pass hold the fixtures that run in every
  configuration; sub-folders run only where they match: solana, pinocchio, bytemuck,
  borsh, wincode, heap (borsh or wincode), and exact pairs such as solana-bytemuck.
- A fixture moves to a sub-folder when a CI run shows its output differs between
  configurations. Moving it means editing the `tests/fail/NAME.rs` path inside its .stderr.
- Snapshots are never generated locally. When one differs, the job reruns with
  TRYBUILD=overwrite and uploads compile-fail-snapshots-RUNTIME-LAYOUT (the regenerated
  .stderr files and wip/). Review them and copy them next to their fixtures. A top-level
  fixture whose regenerated file differs between configurations must move to a sub-folder.
- Coverage: tests/compile-fail/coverage parses derive, syn, core and idl with syn and
  fails when a `Naclac Error:` message has no snapshot, no entry in exemptions.txt and no
  line in uncovered-baseline.txt. The baseline is the open work list; it only shrinks.
  It also requires a valid counterpart tests/pass/PATH for every fail fixture numbered 100
  or above, and checks that fixture folders are valid scopes.
- tests/diagnostics.rs (crate-scan-fixtures) now runs in CI; it was never run before.

Found while building this

- The crate had no lib target, so trybuild dropped feature forwarding to naclac-lang; the

First CI run (2026-11-21) and what it changed
- Framework bug found by the borsh run: `#[defined_type]` on any enum emitted two `#[borsh(..)]`
  attributes, which borsh-derive before 1.8.0 rejects (the framework allows borsh >= 1.6.1).
  derive/src/defined_type/borsh_repr.rs now emits one. The old compile-fail lock pinned borsh
  1.7.0, which is why only this crate saw it.
- Stale tests/compile-fail/Cargo.lock (wincode 0.5.5, solana-address 2.6.1) gave two wincode
  versions in the graph and failed pass/account_seeds.rs under wincode; replaced by the lock of
  tests/enums (wincode 0.6.3, solana-address 2.9.0, borsh 1.8.1). Snapshots that print rustc's
  "other types implement trait" lists depend on resolved versions and must be regenerated.
- Five zero-copy fixtures (03, 45, 46, 47, 49) print those lists, which differ per runtime; they now
  live in fail/solana-bytemuck and fail/pinocchio-bytemuck and need blessed snapshots.
- 01_accounts_pubkey_field imported a solana-only path; it now aliases `Address`, valid on both runtimes.
- #[program] fixtures print many unexpected_cfgs warnings; the owner approved
  `#![allow(unexpected_cfgs)]` for fixtures, added to the four 104 fixtures.
- The coverage scanner missed messages inside attribute argument lists
  (`#[diagnostic::on_unimplemented(message = ..)]`); fixed. An exemption starting with `#[` was
  read as a comment; fixed (comments start with `# `).
- Blessed from CI: fail/heap 100-101, fail/borsh and fail/wincode 102-104, fail/bytemuck 105-107,
  and the ten per-runtime zero-copy snapshots. After the second run (2026-11-21) every fixture passed
  in all five configurations except the 12 that only lacked those snapshots; 108 messages remain
  in uncovered-baseline.txt.

Fixed in the framework (2026-11-21)
- derive/src/system/scale.rs: the tracker now walks every sub-expression (calls, method arguments,
  return, `?`, blocks, if/else, match arms and guards, loops, closures, tuples, arrays, struct literals,
  index, ranges) and checks each arithmetic expression once; nested blocks and branches get their own
  scope. Unit tests in the same file; fixture 192 covers `Ok(a + b)`.
- derive/src/accounts/field/parser/validate.rs: `realloc::any_of` on a field that is not `AccountInfo`
  is a clear error (fixture 191).
- derive/src/accounts/field/parser/attrs.rs: an unknown `realloc::` key is a clear error listing the
  valid keys (fixture 187, snapshot to regenerate).

Round 3 (CI, 2026-11-21)
- The failed run had no pass failures and no mismatches; only 16 fixtures lacked snapshots. All 16
  were identical across the configurations that ran them and were copied in unchanged. Known gaps: 17.
- syn/bounds.rs `more limits than levels` fires only when a recognised shape (`String`, `Vec`, `Option`)
  leaves limits unused; a plain or aliased `u64` goes through the core MaxLen1/2/3 traits instead
  (confirmed from the 179 and 181-183 snapshots). Fixture heap/193 covers the syn site.
- `realloc::zero` was parsed and stored but never used, and `realloc::zero` / `realloc::grow_only` read
  any value other than the literal `true` as false. Changed: `realloc::zero` is removed and
  `realloc::grow_only` is a bare flag. Neither has a dedicated error: `zero` hits the generic
  "`realloc::KEY` is not a constraint" error, which is needed because a bare unknown key (a typo of
  `grow_only`) would otherwise be accepted silently, and `grow_only = true` gets syn's `expected ,`.
  Updated the tracked users: tests/realloc and tests/optional-accounts variants, the pump
  extend_account (`realloc::grow_only,`) and pump-fees extend_fee_config. Fixtures 194-195, 115 and 187
  changed or added; their snapshots are to be regenerated. The checked-in cargo-expand dump
  examples/pump-fun-program/pump-fees/naclac.rs still shows the old key; it is generated output.
